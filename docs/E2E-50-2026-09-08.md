## What a row must prove

Each stage has an explicit `pending`, `pass`, `fail`, `blocked`, or `not-applicable` value. `newConnectedPID` and its kernel start time remain null until observed. `currentStatus` summarizes the complete row; a missing required stage cannot be silently converted to a pass. `evidence` contains this run's artifacts, while `historicalEvidence` stays separate. Record errors and special setup even when later stages succeed.

| Field | Required current evidence |
| --- | --- |
| `nativeInitialLaunch` | The actual production manager/helper opens the selected installed app, with its exact profile, target path and process identity. A standalone CLI compatibility trial is insufficient. |
| `CSSReadback` | The active broker confirms the requested stylesheet text and selected renderer/control identity. A saved enabled flag or successful open request is insufficient. |
| `visual` | Reviewed evidence shows the intended current control and effect. Most test packages use green background/white text; ChatGPT uses hidden sidebar Voice. Record interference from pre-existing styles rather than claiming an unobserved transition. |
| `disableRestore` | Disabling only the owned record removes its contribution and preserves unrelated records/styles. Capture the restored baseline and re-enable result where applicable. |
| `promptShown` | The real native restart prompt appears after the original app is relaunched normally without a healthy extension session. Correlate UI evidence with `promptPresented`; a policy unit test is insufficient. |
| `restartAccepted` | The real prompt's restart action is selected and recorded. The old exact process quits normally; rejection, timeout or a replacement process is retained as an outcome. |
| `newConnectedPID`, `newRuntimeHealthy` | A new process with a fresh kernel identity reaches a healthy active session and the expected CSS effect. `runtimeConnectedOrStarting` in the journal alone does not prove health. |
| `menuLaunch` | An actual app item in the menu is selected, with its request and resulting intended-app activation/identity. Calling the harness's `open` action alone does not prove the menu interaction. |
| `signatureUnchanged` | Strict signature, CDHash and complete bundle fingerprint match the relevant pre-trial baseline while styled and after cleanup. A valid inventory signature alone is insufficient. |
| `cleanup` | Only the owned test record/source is removed; unrelated records, enabled preferences and Dock pins are preserved. Record whether the target remains running and whether the controller/style was removed. No force-quit success claim. |

Recheck versions at each relevant baseline. If an app updates during a trial, record the transition and take a new baseline; do not compare different builds and describe them as one unchanged bundle. Setup, target choice, lifecycle and cleanup evidence must refer to the same recorded run.

## Intended supervised procedure

1. Select one canonical app. Record its current installed identity, signature and full fingerprint, current process/kernel start identity, relevant library record IDs/enabled states, and scoped Dock state. Preserve existing content and account state. Missing apps and unavailable supported routes remain explicit outcomes.
2. Import one owned E2E package through the production manager using the opt-in harness below. Keep the returned record ID. The manager may prepare its signed helper and install the scoped Dock shortcut, as in the product. Preserve all unrelated library records; do not replace the library with a generated batch file.
3. Open through the native manager/helper and wait for the broker's actual healthy state. Verify stylesheet readback, exact renderer/control, current screenshots and integrity. Inspect reports independently of the launch request's return value.
4. Disable the owned record, verify its restoration, and re-enable it. Existing unrelated styles remain enabled; if they already determine the control's appearance, record that limitation rather than inventing a visual before/after difference.
5. Simulate an ordinary launch without the extension session: quit the selected app normally and open its original installed app normally. Observe the native restart prompt. Select its restart action, then verify graceful old-process exit, fresh connected PID/start identity, restored extension effect and intact signing. Do not terminate an unrelated or updater-replacement process to force the sequence.
6. Select the app from the actual menu. Record `menuLaunchRequested`, the intended activation, healthy session and retained CSS. Also exercise the menu's direct list at five or fewer assigned apps, and its Most Used top five plus alphabetical All Tweaked Apps submenu above five, as separate menu-level checks.
7. Remove only the owned test record and inspect the resulting library, CSS/session state, scoped Dock restoration and final integrity. Preserve original records and pins. Keep partial reports and explain any unresolved lifecycle stage before proceeding to the next app.

This procedure uses a **manual normal-relaunch simulation**, not an actual updater installation. Set `actualUpdaterInstallTested: false` unless a separate authorized, observed updater test is performed and documented. The simulation can test loss of debugger launch state and the restart prompt; it cannot establish vendor updater behavior, binary migration or update timing.

## Opt-in test adapter

For ordinary catalog profiles, the full runner performs the procedure above, including actual menu and alert interactions. The desktop must be unlocked. Start with the original target app stopped, a built current manager running, and a new evidence directory:

```sh
node scripts/catalog-native-e2e.mjs bruno \
  "$PWD/output/e2e-50/2026-09-08/live/bruno/trial-NEW"
```

Use a fresh numeric trial suffix in practice. `catalog-e2e-batch.mjs full <slugs…>` allocates fresh numeric directories and runs apps serially. It stops for a locked desktop or cleanup that needs supervision. No trial forces a target app to quit. A successful automated flow still requires inspection of its full-window enabled, disabled, ordinary-launch and restored screenshots before the ledger marks it passed.

`catalog-native-background.mjs` performs only native launch, CSS readback, disable/enable, removal, normal quit and integrity checks. Its images come from the renderer (early trials used control crops; later broker revisions use the complete visible page). It always records `automatedFlowPassed: false`; it cannot establish native full-window, menu, alert or restart proof. A background result never fills a full E2E pass.

Run `node scripts/update-e2e-ledger.mjs --write` to merge saved completed trials and regenerate the table. This command reads evidence; it never starts or changes an app.

[CatalogLiveValidationTests.swift](../macos/Tests/CatalogLiveValidationTests.swift) is a supervised test adapter, not a product automation API. Normal test runs skip it before accessing live state unless both `EA_E2E_ACTION` and `EA_E2E_APP` are set. Each invocation performs one action for one fixed runtime-catalog app, or `chatgpt`/`stylelab`. It uses the real manager, live default library and the built app's fixed resources. Build the current product first.

Use a new evidence filename for every action. This example imports Figma's fixed cosmetic package; it is an intended command, not a claim that the action ran:

```sh
EA_E2E_ACTION=add EA_E2E_APP=figma \
EA_E2E_OUTPUT="$PWD/output/e2e-50/2026-09-08/figma/trial-01/add.json" \
swift test --package-path macos --filter CatalogLiveValidationTests
```

Read `recordID` from that result. Replace `OWNED_RECORD_UUID` below with that exact ID:

```sh
EA_E2E_ACTION=inspect EA_E2E_APP=figma EA_E2E_RECORD_ID=OWNED_RECORD_UUID \
EA_E2E_OUTPUT="$PWD/output/e2e-50/2026-09-08/figma/trial-01/inspect-01.json" \
swift test --package-path macos --filter CatalogLiveValidationTests
```

The actions are `add`, `open`, `disable`, `enable`, `remove`, and `inspect`. Omit the record ID for `add`; subsequent mutations and `open` require it. `inspect` can omit it to report app/session metadata alone. The adapter validates the ID, app key and unique owned name marker, checks unrelated records and ordering after changes, and reports IDs/counts, shortcut paths, process start information and healthy/starting state without emitting stylesheet contents. It refuses existing output files. A post-save failure may still return the created ID so that exact record can be inspected and cleaned up.

The adapter does not click the real restart prompt or menu, take screenshots, or independently establish a full signing round trip. Capture those separately. The native [event journal](../macos/Sources/RuntimeEventJournal.swift) supplies bounded metadata such as `promptPresented`, `restartAccepted`, `restartRequestCompleted`, `runtimeMissing`, `runtimeConnectedOrStarting`, `appActivated` and `menuLaunchRequested`. Correlate it with process identity and actual UI evidence; events describing requests or startup are not completed-action proofs.
