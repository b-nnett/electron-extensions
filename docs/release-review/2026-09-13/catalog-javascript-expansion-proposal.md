# Shared JavaScript support across the curated catalog

Status: the bounded Node/catalog implementation is now complete; see [implementation and evidence](catalog-javascript-expansion-implementation.md). The text below preserves the proposal and its original verification limits.

The next change should make imported CSS/JavaScript a capability of the shared catalog renderer engine, with per-app route and launch constraints as data. It should not require another bespoke script controller for each app.

There are currently **47 catalog profiles**: seven TCP, two LaunchServices TCP and 38 pipe profiles. VSCode and Figma’s login route now use the mixed engine; 45 profiles still reject JavaScript solely because the Node and Swift policies enumerate two identifiers. ChatGPT and the special non-catalog routes are separate adapters and are not covered by this proposal.

## Minimum implementation

1. **Replace duplicated per-app switches with one explicit curated runtime capability.** Add a versioned renderer-runtime field to the bundled catalog, accepting only a fixed engine identifier such as `isolated-js-v1`. Parse the same field in Node and Swift. Only entries from the bundled curated catalog may receive that capability; detecting Electron or finding a matching stored app identifier is insufficient. Keep the existing bundle ID, exact executable/path, ordinary transport arguments and owned-service constraints. Do not add an arbitrary user target, URL, expression, or flag override.
2. **Bind source validation to the selected profile.** Change native mixed policy to carry its validated target identifier instead of maintaining another independent two-ID list. The manager and signed helper derive that policy from the same catalog definition. Node uses the same validated profile to call `selectRendererExtensions`. Preserve limits and legacy-format checks. Tests must show that a library record cannot grant itself a capability by changing `appKey`.
3. **Reuse the existing transport and controller adapters.** TCP and LaunchServices TCP use the current verified loopback listener; pipe uses the owned child’s stdio and grants Runtime only to the chosen attached session. Keep all ownership checks and the unique selected-root check before controller operations. `RendererScriptController`, mixed application, status, recoverable failure semantics, cleanup and bounded attributed logs stay common. All mixed catalog stylesheets use document validation/readback rather than vendor proof controls.
4. **Keep route coverage unchanged during this engine expansion.** Reuse the current curated routes; do not silently widen login routes or choose the first of several matching roots. Retain the stricter VSCode document guard and Figma login guard as profile-specific route constraints. Model further refinements as bounded route types: exact bundle document, exact custom-scheme origin/document, HTTPS origin with bounded path family, or owned-local-service origin. Preserve Antigravity’s separate service/process ownership binding. Broad existing patterns that find multiple roots must continue to refuse, with the limitation recorded.
5. **Run a constrained runtime admission check for each actual launch.** Verify the selected frame, create the isolated world with universal access disabled, require the unique context identity, verify absent Node globals, install the known controller core without CSP bypass, and validate its returned state. Only then apply the user-selected source and report active. Unsupported Runtime methods, Node exposure, a changed route, ambiguous roots or failed bootstrap are explicit per-app failures, not reasons to enable a bypass. User script load errors with completed cleanup keep healthy independent extensions alive and remain inspectable.
6. **Separate available capability from verification history.** A curated app may have the common execution path available while its current version/route has not yet received a complete product proof. Record “not verified,” “verified on version/route,” or “failed with reason” independently of current session health. A successful current session demonstrates its own application; historical CSS evidence must not be relabelled as JavaScript coverage. Login-only results must continue to say login-only. This avoids claiming all 47 work merely because a policy switch changed.

The change makes the same user-selected package executable through every already-curated ordinary interface whose constrained runtime admission succeeds. It preserves failures caused by the app/version/route rather than imposing an artificial CSS-only product policy on otherwise working CDP connections.

## Verification without restarting the 50-app sweep

Use synthetic parity tests over all 47 profile definitions: exact IDs/paths/flags, capability absence/invalid version, source bounds, identity drift, route refusal, duplicate roots, disabled records, recoverable failures, log attribution, and target loss. Add transport-matrix tests for TCP, flattened pipe, and LaunchServices TCP; keep the real owned fixture pipe proof and the existing native VSCode proof as shared-engine anchors.

Then choose a few representative installed apps with ordinary non-login surfaces for real native import → helper → broker → CSS/JS → logs → disable/reload proof: one Chromium file-document pipe app such as Bruno, one custom-scheme app such as Obsidian, and the existing LaunchServices TCP route when its normal surface is available. This validates the architectural classes without resuming the canceled 50-app sweep. Each successful result remains scoped to the exact app/version/route that was exercised.

Several editors within one app are a separate bounded multi-target feature. The current one-root engine must remain honest about that restriction. Before supporting multiple roots, define per-root controller lifetimes, a bounded root count, aggregate source limits, stable attribution/sequence across controllers, and per-root cleanup outcomes. Do not remove ambiguity rejection to simulate that feature.

This is a proposal only. No new app capability, route expansion, vendor launch, or source-policy relaxation was implemented as part of this document.
