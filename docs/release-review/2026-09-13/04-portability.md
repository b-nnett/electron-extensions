# Review 4: clean-machine portability

**Verdict: NO-GO for a public release.** The existing macOS bundle is a development build that depends on the builder's Homebrew Node installation and Xcode's Python. This remains a functional distribution blocker even when DMG creation and installer presentation are excluded.

Reviewed on 2026-09-13 against the source and existing `dist/Extensions Anywhere.app` available during this review. Sparkle integration was being implemented concurrently by the root agent; this is an independent assessment of runtime portability, not an assessment of the final updater changes.

**Follow-up:** The Python dependency below was subsequently removed from production source and replaced with a packaged native reader, with 6 Swift and 19 Node checks passing. See [the implementation and verification](native-identity-fix.md). The findings table preserves the original audit; the final packaged app and separate Node fix must be reassessed before changing the release verdict.

## What already passes

- Packaged JavaScript dependencies are materially better isolated than the old checkout-based runtime. `RuntimeResourceFiles.brokerURL` derives the broker from the current Resources directory; `ElectronLauncher` copies that runtime into each helper, and `LauncherMain` uses its own packaged Runtime as the working directory. The stale absolute broker paths in `LaunchEnvironment.json` are not the runtime relocation problem: the active broker is derived from resources at `ElectronLauncher.swift:366` and `:457`.
- `node --test tests/package-runtime.test.mjs tests/macos-build-settings.test.mjs` passed **10/10 tests**, zero failures. These cover packaged module execution after moving the fixture checkout away, real broker module-graph imports without starting sessions, staging rollback, obsolete-file removal, SDK cache identity, and Mach-O version checks.
- These tests intentionally continue to use the host's `process.execPath` (`tests/package-runtime.test.mjs:33` and `:69`), so passing them does not establish standalone Node portability.
- The current native manager has only system framework/Swift-library links in `otool -L`. The separately referenced Node binary is where the observed Homebrew library dependency closure resides.
- The selected target apps were not launched, modified, re-signed, or otherwise changed by this review. Tests used temporary directories and did not mutate the extension library or Dock.

## Verification limits and release acceptance

No clean macOS VM, Intel Mac, or macOS 14 runtime was available in this review. No distribution upload, notarization submission, app translocation trial, or real update installation was performed. The final Sparkle bundle must be inspected separately after integration because it introduces nested executable code and additional signing/relocation requirements.

The smallest meaningful portability acceptance trial is a downloaded, release-signed app on a fresh user/Mac without Homebrew, Xcode, or Command Line Tools: import a harmless CSS extension for the owned fixture, prepare its launcher, launch and disable it, move the manager app to its supported installation location, reopen the existing helper, and then exercise a signed update. Preserve the existing target-signing checks and record architecture/OS/dependency evidence. Successful execution on the present development Mac is insufficient to close the two dependency blockers.
